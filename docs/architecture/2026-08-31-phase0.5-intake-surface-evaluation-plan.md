## 1. 目標

Phase 0 已證明：

```text
已準備好的 PM inputs
  → AI 生成 React
  → deterministic gates
  → HTTP-rendered prototype
```

Phase 0.5 要補齊第一個真實專案前缺少的三件事：

1. Intake／需求訪談流程，協助 PM 從新需求產生可執行 source-of-truth files；
2. 不會阻擋全新功能的 surface resolution；
3. 能評估整套 prototype-generation workflow 是否可靠的 evaluation harness。

## 2. 核心決策

### 2.1 Intake 先於 Surface

Surface 不能在尚未理解功能前被強制選擇。流程先理解使用者問題、行為、資訊與 review 目標，再決定：

- `reuse`：沿用一個既有 Surface Pack；
- `hybrid`：以一個 pack 為主，組合其他 packs／modules；
- `novel`：沒有合適 pack，建立 feature-specific 暫時版 surface intent。

### 2.2 Surface Pack 是 optional context，不是白名單

`novel` 是合法且不阻擋 PM review 的策略。缺少 pack 不是 design gap，也不是 validation failure；真正的 failure 是 agent 未記錄其 layout intent 與判斷依據就自行猜測。

### 2.3 Intake 與 Update 分開

```text
/prototype-intake <feature>  # 與 PM 訪談並建立／更新 source files
/prototype-update <feature>  # 只讀 source files，生成 derived code
```

這可避免負責生成 code 的 agent 同時偷偷改需求來讓自己的實作通過。

### 2.4 PM draft 與 Designer final 有不同 presentation source

- PM review 階段：`product/surface-intent.yaml` 提供暫時版 presentation intent。
- Designer 提供 final 後：Figma 與 Designer-approved design tokens／references 取得 presentation 優先權。
- PM contract 始終擁有產品行為、state、copy intent、acceptance 與假資料。

Designer 工作方式仍維持建議性質，等 Designer 參與評估後再確定，不在 Phase 0.5 強制。

## 4. Intake workflow

### Step 0 — Create or resume

- 若 feature 不存在，建立空的 source workspace。
- 若已存在，讀取目前 source files 與未決問題，不覆寫已確認內容。
- 不產生 React code。

### Step 1 — Problem and review goal

釐清：

- 要解決什麼使用者問題；
- 主要使用者是誰；
- 主管這一輪需要核准什麼產品決策；
- prototype 是探索概念、確認 flow，還是接近可開發版本。

### Step 2 — Scope and boundaries

釐清：

- in scope／out of scope；
- 入口與成功 outcome；
- 哪些資料一定是假資料；
- 哪些 production／backend 行為只需要模擬；
- 哪些問題必須現在決定，哪些可以成為 open decision。

### Step 3 — State and interaction model

從 PM 語言整理：

- screen／view states；
- user actions；
- transitions；
- empty、loading、success、error 與 recovery；
- copy intent；
- acceptance criteria。

Intake agent 可以提出遺漏情境，但不能替 PM 發明 product policy。

### Step 4 — Surface resolution

依序判斷：

1. 是否有一個既有 pack 能自然承載核心流程？
2. 是否有主要 pack，但需要借用其他 module？
3. 套用既有 pack 是否會迫使使用者採用錯誤 mental model？

輸出 `reuse`、`hybrid` 或 `novel` 建議及理由，由 PM 確認。沒有合適 pack 時直接進入 novel branch，不阻擋。

### Step 5 — Temporary composition intent

整理：

- page zones 與優先層級；
- 必須出現的 component roles；
- 主要／次要 actions；
- 各 viewport 保留與可收合內容；
- 與 pack 不同的 deviations；
- PM temporary UI 的判斷依據。

這裡描述「需要什麼角色與結構」，不重新定義 token values。

### Step 6 — Validation and fake data

- 每個 critical acceptance criterion 都有至少一個 executable check；
- 每個 state／action 都能被驗證或明確標為不需 prototype；
- 建立足以觸發所有路徑的 local mock data；
- 不建立 backend contract 或 production API 假設。

### Step 7 — PM confirmation gate

在寫入正式 source files 前，Intake 顯示一份短摘要：

- problem／goal；
- scope；
- states and actions；
- surface strategy；
- temporary composition；
- acceptance；
- open product decisions；
- decision basis。

PM 確認後才寫入。主管後續 feedback 不需要逐字保存；PM 提出的更新需求直接變成新的 source revision。

## 6. Intake readiness gate

`/prototype-update` 只有在以下條件成立時才能開始：

- PRD、contract、validation、surface intent 與 mocks schema valid；
- feature 的 critical states、actions 與 acceptance IDs 可互相追蹤；
- 所有 critical acceptance criteria 都有 validation check；
- surface strategy 已由 PM 確認；
- `novel` 有 layout intent 與 decision basis；
- product blocker 為零；
- final Figma 可以缺少，Designer gaps 可以存在；
- 所有 prototype data 都是 synthetic。

Surface Pack 不存在本身不會 fail。

## 7. Surface resolver

### Reuse

載入 primary pack 的 layout、component slots、references 與 evaluation rubric。

### Hybrid

- Primary pack 決定 shell 與主要 responsive behavior；
- borrowed packs 只提供指定 roles／modules；
- conflict 必須記錄 resolution，不能讓 agent 默默選擇。

### Novel

- 不載入 visual-similarity baseline；
- 仍載入 RD tokens、shared platform components 與一般 usability rules；
- 依 feature surface intent 產生 DOM anchors 與 functional checks；
- 必須經 PM／主管 review；
- 通過後仍維持 feature-specific，除非另行 promote 成 pack。

## 8. Evaluation harness

### 8.1 Hard gates

任何一項失敗都不能標為 ready：

- PM／Designer source 被 generation agent 修改；
- 未記錄 input hash／generator provenance；
- unknown token／raw visual value；
- backend／external network request；
- build、console、page error；
- critical acceptance path 缺失；
- surface strategy 與 generated layout provenance 不一致。

### 8.2 Functional outcome evaluation

- 從 `validation.yaml` 執行 browser actions；
- 擴充 click 之外的 fill、select、upload mock、keyboard、hover 與 route checks；
- 確認每個 critical state 可到達；
- 在所有 configured viewports 執行；
- 保存 screenshot、DOM／state evidence 與 error trace。

### 8.3 Surface evaluation

- Reuse：檢查 required zones、component slots、layout anchors 與 reference screenshots；
- Hybrid：分別檢查 primary shell 與 borrowed roles；
- Novel：不做不合理的 pack similarity score，改檢查 hierarchy、responsive、design-system compliance 與 feature-specific anchors。

### 8.4 Agent workflow evaluation

在乾淨、隔離的 temporary repo 執行完整 trial，記錄：

- source inputs；
- agent／model／adapter version；
- modified files；
- validation attempts；
- final outcome；
- latency、token／cost（可取得時）；
- trace summary。

以 outcome 為主要評分；trace 只用於 source-boundary、安全、遇到 blocker 是否亂猜，以及失敗診斷，避免強迫 agent 只能走單一路徑。

### 8.5 Mutation tests

至少植入並驗證以下錯誤：

- unknown token；
- external API call；
- stale generation hash；
- acceptance 沒有 executable check；
- generated code 修改 PM source；
- surface pack 缺失但 strategy 錯誤標為 reuse；
- novel feature 沒有 decision basis；
- missing state／error recovery；
- 768px overflow；
- console error。

Evaluator 如果沒有抓到預先植入的錯誤，代表 evaluator 自己失敗。

### 8.6 Initial eval suite

第一版建立 8–12 個 cases：

1. Product Page reuse；
2. Photo Editing Tool reuse；
3. Product Page＋embedded tool hybrid；
4. Image Generator Tool reuse；
5. 完全新的 agent workflow novel；
6. ambiguous requirements，Intake 必須詢問；
7. missing token，必須記錄 gap；
8. 多 state＋error recovery；
9. Designer input absent 的 PM temporary UI；
10. source mutation／network negative case。

## 9. Verdict model

不使用一個可互相抵銷的總分：

- `INVALID`：hard gate failure；
- `FUNCTIONALLY_READY`：critical behavior 與 viewport checks 通過；
- `PM_REVIEW_READY`：surface／hierarchy／usability evaluation 通過；
- `DESIGN_FINAL_READY`：Phase 1 的 Designer final、YCO-spec 與 independent review 完成。

Novel surface 可以達到 `PM_REVIEW_READY`，不需要先變成 Surface Pack。

## 11. Definition of Done

- 新 feature 可以在沒有既有 Surface Pack 時完成 Intake 與 PM review prototype；
- Intake 與 generation 權責分離；
- PM source changes 能使 generated artifact 正確失效；
- reuse／hybrid／novel 都有 executable tests；
- 所有 seeded mutation 都被 evaluator 抓到；
- 第一個真實 pilot 的 critical behavior、三 viewport 與 console checks 全數通過；
- PM 能閱讀 eval report，知道失敗發生在 input、generation、function、surface 或 grader；
- 文件包含決策及判斷依據。

## 12. 判斷依據

- 新 feature 可能沒有既有頁型，因此 Intake 必須先於 surface resolution。
- Pack 適合降低 generic UI 與重複設計，但不能犧牲產品探索能力。
- Intake 與 Update 分離可保護 PM source of truth，避免 agent 為了讓 code 通過而改需求。
- PM-only 階段仍需要 temporary presentation intent；等 Designer final 到位後再切換 presentation authority。
- 單次 build／Playwright PASS 只能證明一個 artifact，不能證明 generation workflow 在不同需求與模型下可靠。
- Deterministic、browser、visual、model 與 human evaluation 必須分層，因為任何單一 grader 都會漏掉不同類型的錯誤。
- Mutation tests 能驗證 evaluator 是否真的有偵測能力，避免產生只會報 PASS 的 vanity evaluation。
- 先實作 pilot 需要的少量 packs，可降低 migration 時間並避免把尚未查證的舊 surface 規則變成新 source of truth。
